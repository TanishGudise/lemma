A **monitor** is a continuously running tracker attached to one agent. It examines that agent’s traces and records when a specific event or behavior occurs.

The description tells the monitor what to look for. Each match updates its count and percentage. A behavior monitor also writes an issue when the agent gets that behavior wrong.

Use a monitor to track:

- How many times a user gets frustrated
- How many times an agent uses a tool wrong
- How many times an agent incorrectly cancels a reservation

Open **Monitors** in a project in the [Lemma dashboard](https://platform.uselemma.ai).

## Signal or behavior

You choose the kind when you create the monitor. It does not change later. Pick the kind by what you want back:

- **Signal**: records when an event occurs, with no issues. User frustration is a signal.
- **Behavior**: records when a behavior is wrong and writes an issue. A wrong tool call or cancellation is a behavior.
- **Template**: one monitor for each starter you pick

Those issues are separate from failures Lemma groups on its own. Alerting still follows the [issue lifecycle](/platform/issues).

## Create a monitor

**New monitor** asks for these, in order:

1. **Agent to watch.** Pick the one agent this monitor judges. You can’t change it later. Lemma does not judge a trace that has no agent name.
2. **Kind.** Choose **Signal**, **Behavior**, or **Template**.
3. **Name.** This is the label on the card. Lemma does not look for a tool call with that name.
4. **Scenario**, on a behavior monitor. Describe what the agent should do.

For a wrong cancellation, name the request, the right action, and the mistake:

- Good: “A guest asks to cancel a stay. The agent cancels that reservation, and no other.”
- Bad: “Handle cancellations.”

On a signal monitor, **Which traces count** is optional. Use it to say what to count and what to skip.

## Percent and count

Each matching trace updates the count. The chart draws one point per day.

<Frame>
  <img src="/images/platform/monitors-detail.png" alt="Rate Binder monitor with a percent chart, one point per day, a Count toggle, and the Quoting group" />
</Frame>

**Percent** is the share of that day’s traces that fit. **Count** is how many traces fit that day. A behavior monitor also shows how many of those traces have an occurrence.

You can view the same chart by week or by month. Until the monitor has seen a trace, there is no percent yet.

## When a trace is wrong

Tell Lemma, then recalibrate. The chart and the trace list update from the correction. **Recalibrate** teaches the monitor for later traces. Lemma also does that every night, and skips a night with no new feedback.

**Doesn’t fit** and **Mark incorrect** mean this trace should not count. **Add to monitor** means it should, including a trace the monitor has not judged. You can add a short reason. On **Traces** and **Issues**, you can mark several rows at once.

One monitor keeps one correction per trace. **Undo**, or **Restore** on **Feedback**, puts the trace back. A succeeded recalibrate removes the feedback it used. If a recalibrate is already running, Lemma refuses another.

A wording change stays a suggestion until you accept it. Dismiss the suggestion to keep the saved wording. A failed or skipped run leaves that feedback in place.

The count rules and the learning window are in the [monitor contract](/reference/monitor-contract#corrections-and-counts). Use that page when a chart does not match the trace you marked.

## Groups

**All monitors** lists every monitor in the project. **New group** adds a tab you name, and a monitor can belong to more than one group. **Existing** appears only inside a group, and adds monitors you already have.

Deleting a group leaves its monitors running. Everyone in the project sees the same groups and the same card order. Card order, creating on an open group tab, and the side rail are in the [monitor contract](/reference/monitor-contract#groups-and-the-board).

## From the API

REST and the [Lemma Model Context Protocol (MCP) server](/connections/mcp) share the reads. You create a monitor, change it, record feedback, and recalibrate on REST. What those calls change is in the [monitor contract](/reference/monitor-contract#from-the-api). Request shapes are in the [API Reference](/api-reference).
